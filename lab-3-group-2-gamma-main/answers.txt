/******************************************************************************
** Task: Running the slow program
**
** 1. What is the complexity of findSimilarity?
**    Answer in terms of N, the total number of 5-grams in the input files.
**    Assume that the number of 5-grams that occur in more than one file
**    is a small constant - that is, there is not much plagiarised text.
******************************************************************************/
The brute-force method contains four nested loops: for path1, for path2, for ngram1, for ngram2.
If $N$ is the total number of 5-grams across all files, this logic effectively compares every single 5-gram against every other 5-gram in the entire dataset.
Therefore, the baseline complexity is $O(N^2)$. (Depending on how the BST is implemented, the put/contains methods might add an additional $O(\log N)$ factor, resulting in $O(N^2 \log N)$).


/******************************************************************************
** 2. How long did the program take on the 'small' and 'medium' directories?
**    Is the ratio between the times what you would expect, given the complexity?
**    Explain very briefly why.
*******************************************************************************/
Small Time: 1.74s
Medium Time: 315.93s
Input Size Increase: $N_{medium} / N_{small} = 200,000 / 20,000 = 10$. The input is 10 times larger.
Expected time increase: Because it is $O(N^2)$, the expected time should be $10^2 = 100$ times longer.

The theoretical ratio should be 100x because the input size increased by a factor of 10, and the algorithm is $O(N^2)$ ($10^2 = 100$).
However, the actual ratio was closer to 182x approx 200x. 
This happens because our $O(N^2)$ assumption relied on the amount of plagiarised text (shared n-grams) being a small constant.
The medium dataset contains a higher density of plagiarised text than the small dataset, causing the innermost loops of the brute-force search to trigger and execute much more frequently,
therefore drastically increasing the constant factor of the runtime.

/******************************************************************************
** Task: Using binary search trees
**
** 4. Which of the trees usually become unbalanced?
******************************************************************************/
 The files BST will become highly unbalanced. 
 Inserting pre-sorted data into a standard Binary Search Tree causes it to degrade into a linked list, where every new node is added as a right child.
 This turns your $O(\log N)$ lookups into $O(N)$ worst-case lookups.


/******************************************************************************
** 5 (optional). Is there a simple way to stop these trees becoming unbalanced?
******************************************************************************/
Randomize (shuffle) the paths array after reading it from the directory but before inserting it into the BST.

Use a self-balancing binary search tree a Scapegoat tree, AVL tree or Red-black tree.


/******************************************************************************
** Task: Using scapegoat trees
**
** 6. Now what is the total complexity of buildIndex and findSimilarity?
**    Again, assume a total of N 5-grams, and a constant number of 5-grams
**    that occur in more than one file.
******************************************************************************/
buildIndex: Inserting $N$ items into the tree takes $O(N \log N)$ time.

findSimilarity: You iterate over the index. The assumption states there is a constant number of shared n-grams, 
meaning the nested loops inside findSimilarity execute a constant $O(1)$ amount of times per n-gram.
 Looking up/putting into the similarity tree takes $O(\log N)$. 
 Thus, this phase also takes $O(N \log N)$.

 The total time complexity for both phases combined is strictly $O(N \log N)$.

/******************************************************************************
** 7 (optional). What if the total similarity score is an arbitrary number S,
**               rather than a small constant?
******************************************************************************/
 If there are $S$ similar file pairs discovered, the inner loop of findSimilarity will execute exactly $S$ times.
 Inside that loop, you do a lookup/insertion into the similarity Scapegoat tree, which currently holds at most $S$ elements.
 Therefore, the time spent building the similarity tree becomes $O(S \log S)$.

The new total complexity for the entire program becomes $O(N \log N + S \log S)$.
